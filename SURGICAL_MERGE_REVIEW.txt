EXACT DATABASE PATH FINDINGS
Target main server/index.js never opens the database or reads DB_PATH. It
imports nonexistent default exports from db.js and services.js and cannot
start as written. Its mocked transfer route is not evidence of settlement.
Donor root server/index.js uses configuration().dbPath:
  options.dbPath ?? resolve(process.env.DB_PATH || resolve(root,'data/bank.sqlite'))
An explicit relative DB_PATH resolves against process.cwd(); an omitted value
defaults to the root application's own data/bank.sqlite.
Donor SVBT/server/index.js uses the same expression, but root is the nested
SVBT directory, so the omitted default is SVBT/data/bank.sqlite.
The donor root also automatically provisions published demo accounts even
in production. That startup behavior was excluded from the integration.
The integrated root retains relative-path compatibility for development and
createApp tests. Executable production startup requires explicit absolute
DB_PATH and STATEMENT_DIR and an existing database before opening/migrating it.
The backup and restore commands now share the application-root default path.

DATABASE, PERSISTENCE AND BACKUP
Database engine: built-in node:sqlite DatabaseSync, not better-sqlite3.
WAL, foreign keys, 5-second busy timeout, atomic writes and immutable ledger,
audit and issued-statement records are retained. Donor migrations 1–6 are
included; new migrations 7 and 8 add batch receipts and legacy site tables.
A database schema newer than the application is refused.
The existing root render.yaml remains unchanged: it uses a free plan and
relative DB/statement paths, with no persistent disk. It is not ready for this
production startup guard and must not be deployed unchanged.
deploy/render.production.proposed.yaml is a separate REVIEW-ONLY proposal:
paid starter service, 1 GB /var/data disk, absolute database/statement paths,
manual deployments, health endpoint and secret placeholders. It passed the
current Render 2020-12 JSON schema. No Render sync/validation API was invoked.
Blueprint Final's resource association still requires confirmation before use.

The connector exposes neither the live filesystem nor backup inventory.
Actual runtime DB_PATH/STATEMENT_DIR, database contents/size, disk placement,
backup existence, off-service retention and recoverability remain unverified.
A mounted disk does not establish that the database is stored on that disk.
No assumption was made that any database is disposable.
The included backup helper uses SQLite VACUUM INTO, integrity validation,
gzip and SHA-256, and is tested with committed WAL data. It was NOT run against
production. Restore requires a matching checksum and valid SQLite structure,
rejects an existing target or orphan WAL/SHM, cleans failed staging files and
publishes with an atomic no-clobber link. Restore-pending health returns 503.
Statement PDFs remain stored in SQLite; archive integrity supports the current
statement directory without rewriting immutable issued records.
